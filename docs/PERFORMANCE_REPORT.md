## 1. Objective and outcome

Measure the Todo list and count workload on a representative PostgreSQL dataset,
add the smallest index that serves both queries, and quantify read, write, and
storage impact.

The accepted index is `(user_id, created_at, id)`. PostgreSQL scans it backward
for `created_at DESC, id DESC`, and its `user_id` prefix also supports the count.
This avoids retaining a second overlapping `user_id` index.

| Query | Baseline median | Optimized median | Speedup | Baseline p95 | Optimized p95 |
|---|---:|---:|---:|---:|---:|
| Q1: user page | 22.245 ms | 0.056 ms | 397.2× | 29.735 ms | 0.215 ms |
| Q2: user count | 20.471 ms | 0.064 ms | 322.4× | 21.038 ms | 0.097 ms |

## 4. Exact workload SQL

The reproducible SQL is tracked in
[`performance/benchmark.sql`](performance/benchmark.sql).

### Q1 — user-scoped Todo page

This is the SQL generated by `TodoService.get_todos` after adding deterministic
pagination order:

```sql
SELECT id, title, description, completed, user_id, created_at, updated_at
FROM todos
WHERE user_id = '1bbd9104-7e50-42a9-bc2d-d62886d27cce'::uuid
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 0;
```

### Q2 — user-scoped Todo count

```sql
SELECT count(*)
FROM todos
WHERE user_id = '1bbd9104-7e50-42a9-bc2d-d62886d27cce'::uuid;
```

Status and Tag filters were added after this Tier 3C benchmark and were not
measured in this report. No hypothetical result is presented as application
evidence; a future benchmark must use the current filter SQL and representative
Tag selectivity before claiming an index benefit for those paths.

## 5. Measurement method

1. Create the dedicated PostgreSQL database and migrate it to `a0790c76a129`.
2. Seed 10,000 users and 1,000,000 Todos, then run `ANALYZE users; ANALYZE todos;`.
3. Confirm that `todos_pkey` is the only baseline Todo index.
4. Capture `EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT TEXT)` for Q1 and Q2.
5. Execute 10 additional sequential `EXPLAIN ANALYZE` samples per query and
   calculate median and continuous p95. No sample was discarded.
6. Apply Alembic revision `c3d5e7f9a1b2` and repeat identical SQL/parameters.
7. Downgrade and re-upgrade the migration on the one-million-row database.
8. Measure 10 inserts and 10 updates before/after inside transactions that are
   rolled back, keeping the dataset unchanged.

All 40 read samples and 40 write samples are retained in
[`performance/timings.csv`](performance/timings.csv).

## 7. Index decision

| Candidate | Benefit | Cost | Decision |
|---|---|---|---|
| `(user_id, created_at, id)` | Q1 filtering/order, stable pagination, and Q2 prefix count | Every insert maintains one 56 MB B-tree | Accepted |
| `(user_id)` | Q2 and filtering only | Overlaps the accepted index prefix; cannot supply Q1 order | Rejected |
| `(user_id, completed, created_at, id)` | Useful only for a future status filter | Adds storage/write cost and cannot order the unfiltered Q1 result without a sort | Rejected until that workload exists and is measured |

PostgreSQL can scan a B-tree backward, so an ascending physical definition
supports both descending order columns without a separate descending index.

## 8. Implementation

| Change | Location | Reason |
|---|---|---|
| Stable `created_at DESC, id DESC` order | `backend/app/services/todo_service.py` | Deterministic pages and direct use of the composite index |
| Matching SQLAlchemy index metadata | `backend/app/models/todo.py` | Keep runtime model and migrations aligned |
| Concurrent Alembic index migration | `backend/alembic/versions/c3d5e7f9a1b2_add_todo_user_created_index.py` | Avoid blocking writes while PostgreSQL scans/builds |
| Ordering regression | `backend/tests/test_todos.py::test_get_todos_orders_newest_first` | Prevent removal of stable order |

The migration uses Alembic's autocommit block because PostgreSQL forbids
`CREATE INDEX CONCURRENTLY` and `DROP INDEX CONCURRENTLY` inside a transaction.
Measured wall-clock time on this local one-million-row table was 1.30 seconds on
the first upgrade, 0.64 seconds for downgrade, and 1.35 seconds for re-upgrade;
these values include Compose exec and Alembic startup overhead.

## 10. Write and storage impact

Write queries were wrapped in `BEGIN`/`ROLLBACK`. Inserts used the benchmark
user; updates toggled `completed` for fixed Todo
`02893942-c77a-4e2b-b338-b03748ac392d`, which is not part of the new index.

| Measurement | Before | After | Difference |
|---|---:|---:|---:|
| Insert median, n=10 | 0.434 ms | 0.458 ms | +0.024 ms / +5.5% |
| Insert p95, n=10 | 0.961 ms | 0.860 ms | -0.101 ms; sample noise dominates |
| Update median, n=10 | 0.104 ms | 0.103 ms | -0.001 ms; effectively unchanged |
| Todo table | 222,101,504 bytes (212 MB) | 222,101,504 bytes (212 MB) | none |
| Todo indexes | 39,485,440 bytes (38 MB) | 98,394,112 bytes (94 MB) | +58,908,672 bytes (56 MB) |
| Todo total relation | 261,677,056 bytes (250 MB) | 320,585,728 bytes (306 MB) | +58,908,672 bytes (22.5%) |

The insert median shows the expected B-tree maintenance cost. The small sample
and sub-millisecond writes are sensitive to scheduling noise, so the negative
p95 difference is not treated as an improvement. Updates to `completed`, title,
or description do not change indexed columns and can remain HOT-eligible where
page space permits; changing `user_id`, `created_at`, or `id` must update the
index.

The extra index also increases WAL, backup size, cache pressure, vacuum work,
and write amplification. `ANALYZE` should run after large backfills so the
planner has current per-user cardinality estimates.

## 11. Migration safety

- **Lock behavior:** `CREATE INDEX CONCURRENTLY` performs multiple scans and
  takes brief metadata locks without blocking normal inserts, updates, or
  deletes for the full build. It takes longer and uses more I/O than a normal
  index build.
- **Transaction behavior:** the revision deliberately uses an Alembic
  autocommit block. A larger multi-operation schema change must not assume this
  index build rolls back atomically with surrounding DDL.
- **Disk headroom:** allow at least the final index size plus temporary build,
  WAL, and safety margin. This dataset produced a 56 MB index; production
  rollout should reserve materially more than 56 MB per million similarly sized
  rows and verify on a production-like snapshot.
- **Failure/retry:** a failed concurrent build can leave an `INVALID` index.
  Before retry, inspect `pg_index.indisvalid`; drop an invalid index concurrently,
  then rerun the revision.
- **Monitoring:** watch `pg_stat_progress_create_index`, database I/O latency,
  WAL generation/replication lag, deadlocks, free disk, and application p95/p99
  write latency.
- **Rollback:** `alembic downgrade a0790c76a129` uses `DROP INDEX CONCURRENTLY`.
  Downgrade and re-upgrade both passed against the one-million-row database.
- **Deployment sequencing:** deploy the index before code that depends on its
  performance. The ordered query remains functionally correct without it, so
  rollback of application code is independent of retaining the index.

The 1.30-second local build is evidence for this environment only, not a
production duration estimate. Build time scales with rows, tuple width, storage
throughput, concurrent writes, WAL/replication, and cache state.

## 12. Limitations

- The seed distributes Todos nearly uniformly; a heavy tenant with far more
  than 142 rows needs separate deep-page and high-cardinality measurements.
- Q1 measures offset 0. Large offsets still require scanning/skipping index
  entries; keyset pagination should be evaluated for deep navigation.
- Timing was measured on Docker Desktop with warm caches and no concurrent load,
  not production hardware.
- The dataset was generated randomly, but exact counts, selected user, query
  parameters, raw plans, and every sample are retained for this run.
- Status/Tag queries were not measured in this Tier 3C run. Capture a new
  PostgreSQL baseline with representative selectivity before claiming an index
  benefit for the delivered Tier 4 filters.

## 13. Reproduction

```bash
# Configure ignored local environment values first.
cp .env.example .env

# Start PostgreSQL/backend and create an isolated benchmark database.
docker compose up -d --build --wait postgres redis backend
docker compose exec postgres sh -c \
  'createdb -U "$POSTGRES_USER" fabbi_performance'

# Point Alembic/seed at fabbi_performance using the same credentials as the
# normal backend DATABASE_URL, then migrate only through a0790c76a129 to capture
# baseline evidence.
docker compose exec backend sh -c \
  'DATABASE_URL="${DATABASE_URL%/*}/fabbi_performance" alembic upgrade a0790c76a129'

docker compose exec -T \
  -e SEED_USERS=10000 \
  -e SEED_TODOS=1000000 \
  -e SEED_USER_BATCH_SIZE=1000 \
  -e SEED_TODO_BATCH_SIZE=10000 \
  backend sh -c \
  'DATABASE_URL="${DATABASE_URL%/*}/fabbi_performance" python -m app.db.seed'

docker compose exec -T postgres sh -c \
  'psql -U "$POSTGRES_USER" -d fabbi_performance' \
  < docs/performance/benchmark.sql

# Apply and verify the index, then repeat benchmark.sql.
docker compose exec backend sh -c \
  'DATABASE_URL="${DATABASE_URL%/*}/fabbi_performance" alembic upgrade head'
docker compose exec -T postgres sh -c \
  'psql -U "$POSTGRES_USER" -d fabbi_performance' \
  < docs/performance/benchmark.sql
```

The shell redirection supplies the tracked SQL through container stdin; it does
not require PostgreSQL/Redis host ports. Reviewers should select their run's
highest-volume user and update `benchmark_user` in the SQL file after seeding.
